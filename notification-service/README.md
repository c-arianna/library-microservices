## Overview

The Notification Service is responsible for delivering platform notifications to end users.

The service acts as a bridge between the event-driven backend and client-facing communication channels, consuming notification events from RabbitMQ and delivering 
them through real-time WebSocket updates and SMS notifications.

The service is intentionally isolated from business domains and focuses exclusively on communication and user engagement concerns.

## Responsibilities

The service provides the following capabilities:

- real-time notifications through WebSockets;
- targeted user notifications;
- subscription availability notifications;
- SMS delivery abstraction;
- notification event processing;
- notification event publication;
- WebSocket authentication and authorization.

## Architectural Role

The service acts as the communication layer of the platform.

```text
Book Service
Loan Service
User Service
        │
        ▼
 Notification Events
        │
        ▼
 RabbitMQ
        │
        ▼
Notification Service
        │
        ├── WebSocket Notifications
        ├── User-Specific Notifications
        └── SMS Notifications
```

The service translates backend events into user-facing communication channels without introducing direct coupling between domain services and presentation concerns.

## Event Processing

The service consumes notification events generated by other modules.

Incoming events are routed to dedicated handlers according to:

- notification event type;
- schema version.

A notification handler registry guarantees that only supported event versions are processed.

### Supported Notification Events

The service currently processes:

- BOOK_UPDATED
- BOOK_REQUEST_UPDATED
- LOAN_UPDATED
- USER_UPDATED
- BOOK_SUBSCRIPTION_REQUESTED

## Notification Channels

### WebSocket Notifications

The service exposes a STOMP/WebSocket endpoint:

```text
/ws/notifications
```

and publishes notifications to topics such as:

- `/topic/books` for catalogue updates and book availability notifications;
- `/topic/bookRequests` for purchase request updates;
- `/topic/loans` for loan lifecycle notifications;
- `/topic/users` for user management notifications.

Notifications received through RabbitMQ are translated into WebSocket messages and delivered in real time to connected clients.

### User-Specific Notifications

Private notifications are delivered through user queues:

- `/user/queue/loans` for loan lifecycle notifications
- `/user/queue/users` for user management notifications

allowing notifications to be sent only to the intended recipient.

### SMS Notifications

Subscription-related notifications can be delivered through SMS.

An abstraction layer is provided through the `SmsSender` interface, allowing different SMS providers to be integrated without impacting business logic.

The current implementation includes a development-oriented fake sender used for testing and demonstration purposes.

## Produced Events

The service publishes notification-related integration events.

Currently supported events include:

- BOOK_SUBSCRIPTION_NOTIFIED

These events are published after successful notification processing and can be used by other services to track notification workflows.

## Consumed Events

### Book Service Notifications

The service processes notifications related to:

- catalogue updates;
- book availability;
- inventory changes;
- purchase request status updates;
- subscription availability alerts.

### Loan Service Notifications

The service processes notifications related to:

- loan creation;
- loan reservations;
- loan confirmations;
- loan returns;
- loan failures.

### User Service Notifications

The service processes notifications related to:

- user registration;
- suspensions;
- reactivations;
- library card assignment.

## Service Interactions

### Book Service

Consumes catalogue-related events and subscription-related events to generate user notifications.

### Loan Service

Consumes loan-related events and delivers user-facing notifications.

### User Service

Consumes user-related events and delivers user management notifications.

## Security

The service integrates with Keycloak and validates JWT tokens for WebSocket connections.

Authentication is performed during the STOMP connection handshake through JWT validation.

Role-based authorization controls access to notification topics.

Examples include:

- authenticated users may subscribe to book notifications;
- only librarians and administrators may subscribe to loan and user management topics.

## WebSocket Authorization

Access to notification channels is controlled through Spring Security authorization rules.

| Destination | Access |
|------------|----------|
| `/topic/books` | Authenticated users |
| `/topic/bookRequests` | Authenticated users |
| `/topic/loans` | LIBRARIAN, ADMIN |
| `/topic/users` | LIBRARIAN, ADMIN |
| `/user/**` | Authenticated users |

## Observability

The service participates in platform-wide distributed tracing.

Notification publication and processing include tracing information that can be correlated through Zipkin to support end-to-end workflow monitoring.

## Testing Strategy

The module includes:

- notification handler tests;
- event publisher tests;
- event listener tests;
- handler registry tests;
- WebSocket notification verification.

Tests validate:

- payload mapping;
- notification routing;
- handler version resolution;
- error handling;
- event publication logic.

## Deployment

The service is containerized using Docker and participates in the platform Docker Compose environments used for development, testing and end-to-end validation.

A Dockerfile is provided to build the service image used by the development and testing environments.

The service does not maintain its own database and relies on RabbitMQ and WebSocket infrastructure to perform its responsibilities.
