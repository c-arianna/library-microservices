## Overview

The Book Service is responsible for managing the library catalogue and book purchase workflows.

It implements Domain-Driven Design (DDD), Event Sourcing and CQRS-inspired architectural patterns to separate command processing from query operations. 
In addition to catalogue management, the service handles book reservations, subscriptions, purchase requests and inventory availability.

The service plays a central role within the platform, acting as the system of record for books and coordinating several event-driven interactions with other 
microservices.

## Responsibilities

The service provides the following capabilities:

- catalogue management;
- book registration;
- copy availability management;
- book reservations;
- subscription management;
- purchase request workflows;
- purchase request voting;
- purchase request approval and rejection;
- purchase suggestion generation;
- projection management and rebuilding.

## Domain Model

The service is structured around two primary aggregates.

### Book Aggregate

The Book Aggregate manages the lifecycle of books and copies within the catalogue.

Key responsibilities include:

- registering books;
- managing available copies;
- reserving books for loans;
- handling returns;
- releasing reservations.

### Book Request Aggregate

The Book Request Aggregate manages user-generated book purchase requests.

Key responsibilities include:

- creating purchase requests;
- collecting votes;
- updating estimated prices;
- approving requests;
- rejecting requests.

## Architectural Patterns

The service implements several architectural patterns commonly used in enterprise systems:

- Domain-Driven Design (DDD)
- Event Sourcing
- CQRS
- Outbox Pattern
- Event Replay
- Event-Driven Communication

### Event Sourcing

The current state of the domain is derived from persisted domain events rather than direct state mutations.

Aggregates rebuild their state by replaying historical events and validating event versions to ensure consistency.

### CQRS

The service separates:

- Write Model (Aggregates and Commands)
- Read Model (Projections and Views)

Read operations are performed against dedicated projections optimized for querying.

### Outbox Pattern

Event publication is implemented through the Outbox Pattern: this approach ensures transactional consistency between event persistence and event publication.

Domain events are persisted in both:

- the event store;
- the outbox table.

A scheduled publisher reads pending outbox entries and publishes integration events to RabbitMQ, ensuring reliable event delivery.

### Event Replay

The service supports rebuilding projections by replaying historical events stored in the event store.

Replay processing supports:

- projection recovery;
- projection evolution;
- consistency validation;
- rebuilding read models without modifying historical events.

Dedicated replay repositories rebuild temporary projections and promote them to production views only after successful completion.

## Event Processing

The service distinguishes between domain events and integration events used for inter-service communication.

### Domain Events

Domain events represent business changes within the Book Service bounded context.

They are:

- generated by aggregates;
- persisted in the event store;
- used to rebuild aggregate state;
- transformed into integration events used for projection updates and inter-service communication;
- internal to the originating service.

### Integration Events

Integration events are generated from persisted domain events and published through RabbitMQ.

They provide stable contracts for communication with other services and allow the domain model to evolve independently from inter-service integrations.

The Outbox Pattern guarantees reliable publication of integration events and prevents data-loss scenarios during message delivery.

## Consumed Events

The service consumes events originating from the Loan Service.

Supported workflows include:

- loan requests;
- loan confirmations;
- loan cancellations;
- book returns.

Incoming events trigger aggregate operations that update the domain state and generate new domain events.

It also consumes events originating from the User Service to update its user projection.

## Service Interactions

### Loan Service

Consumes loan-related events and publishes book reservation and borrowing outcomes.

### User Service

Consumes user-related events and maintains user projections used by business workflows.

### Notification Service

Publishes catalogue-related events that are consumed by the Notification Service to notify users about:

- newly registered books;
- changes in book availability;
- copy inventory updates;
- subscription-based availability notifications when requested books become available again.

## Read Model and Projections

The service maintains dedicated projections that provide optimized query capabilities.

The available projections are:

- Book Projection
- Book Request Projection
- Book Request Vote Projection
- Book Subscription Projection
- User Projection

These projections are updated asynchronously through event handlers and can be rebuilt through replay operations.

## Security

The service acts as an OAuth2 Resource Server and validates JWT tokens issued by Keycloak.

Authorization is role-based and supports:

- READER
- LIBRARIAN
- ADMIN

Roles are extracted directly from JWT claims and applied through Spring Security authorization rules.

## Observability

The service integrates with Zipkin for distributed tracing and participates in platform-wide observability workflows.

Tracing information is propagated through published and consumed events to support end-to-end request tracking.

## Deployment

The service is containerized using Docker and participates in the platform Docker Compose environments used for development, testing and end-to-end validation.

A Dockerfile is provided to build the service image used by the development and testing environments.
