## Overview

The User Service manages users within the Library Platform.

It is responsible for user registration, profile management, role assignment, account lifecycle management and integration with the platform identity provider.

The service follows an Event Sourcing architecture and maintains both an event store and materialized read models. 
It also publishes integration events and notifications to keep the rest of the platform synchronized with user-related changes.

## Responsibilities

The service manages:

- user registration and subscription;
- user profile information;
- account suspension and reactivation;
- account deactivation;
- role assignment;
- library card assignment;
- identity provider synchronization;
- user read models and projections.

## Architectural Patterns

The service adopts:

- Event Sourcing;
- CQRS;
- Outbox Pattern;
- asynchronous event-driven communication;
- projection replay capabilities.

Domain changes are stored as immutable events while read-optimized projections provide efficient query access for client applications.

### Event Sourcing

The current state of the domain is derived from persisted domain events rather than direct state mutations.

The aggregate lifecycle is reconstructed from the event stream and supports optimistic versioning through event ordering.

The event store tracks all domain-level changes and serves as the source of truth for the user domain.

### CQRS Read Model

The service maintains dedicated user projections for query operations.

The read model stores:

- user identity information;
- roles;
- account status;
- library card information;
- identity provider identifiers.

Projections are updated asynchronously through integration event processing and provide efficient query capabilities independent from the event store.

### Outbox Pattern

Event publication is implemented through the Outbox Pattern: this approach ensures transactional consistency between event persistence and event publication.

Domain events are persisted in both:

- the event store;
- the outbox table.

A scheduled publisher reads pending outbox entries and publishes integration events to RabbitMQ, ensuring reliable event delivery.

### Event Replay

The service supports rebuilding projections by replaying historical events stored in the event store.

Replay processing supports:

- projection recovery;
- projection evolution;
- consistency validation;
- rebuilding read models without modifying historical events.

Dedicated replay repositories rebuild temporary projections and promote them to production views only after successful completion.

## Event Processing

The service distinguishes between domain events and integration events used for inter-service communication.

### Domain Events

Domain events represent business changes within the User Service bounded context.

They are:

- generated by aggregates;
- persisted in the event store;
- used to rebuild aggregate state;
- transformed into integration events used for projection updates and inter-service communication;
- internal to the originating service.

The service produces the following domain events:

- UserSubscribedEvent;
- UserUnsubscribeEvent;
- UserSuspendEvent;
- UserUnsuspendedEvent;
- LibraryCardAssignedEvent.

These events are transformed into integration events that are consumed by other platform services to maintain distributed consistency.

The service does not consume integration events produced by other services.

### Integration Events

Integration events are generated from persisted domain events and published through RabbitMQ.

They provide stable contracts for communication with other services and allow the domain model to evolve independently from inter-service integrations.

The Outbox Pattern guarantees reliable publication of integration events and prevents data-loss scenarios during message delivery.

## User Lifecycle

The service supports the complete lifecycle of a user.

Supported operations include:

- user subscription;
- administrative user creation;
- profile retrieval;
- user suspension;
- user reactivation;
- user unsubscription;
- library card assignment.

Users can move between the following states:

- ACTIVE;
- SUSPENDED;
- DISABLED.

## Identity Provider Integration

The service integrates with Keycloak for identity management.

Responsibilities include:

- user creation;
- account deletion;
- role assignment;
- administrative user provisioning;
- synchronization between the library domain and the identity provider.

This separation allows authentication concerns to remain independent from business logic while maintaining consistency across the platform.

## Library Card Management

Reader users are assigned a unique library card number.

The service provides automatic card generation and unique card sequencing.

Administrative and librarian accounts do not require library cards.

### Data Migration Support

The service includes dedicated migration capabilities for historical data evolution.

A migration process is available to assign library card numbers to legacy users created before card support was introduced in the application.

## Service Interactions

### Book Service

Publishes user-related events consumed by the Book Service to maintain user projections and subscription workflows.

### Loan Service

Publishes user-related events consumed by the Loan Service to maintain user projections and loan-related workflows.

### Notification Service

The service publishes notification events that are consumed by the Notification Service to inform users about updates to their account data.

Supported notifications include:

- USER_UPDATED.

Notifications provide downstream consumers with updated user information without exposing internal implementation details.

## Security

The service acts as an OAuth2 Resource Server and validates JWT tokens issued by Keycloak.

Authorization is role-based and supports:

- READER;
- LIBRARIAN;
- ADMIN.

Access permissions are enforced both at API and application level.

## Observability

The service integrates with Zipkin for distributed tracing and participates in platform-wide observability workflows.

Tracing information is propagated through published and consumed events to support end-to-end request tracking.

## Deployment

The service is containerized using Docker and participates in the platform Docker Compose environments used for development, testing and end-to-end validation.

A Dockerfile is provided to build the service image used by the development and testing environments.
