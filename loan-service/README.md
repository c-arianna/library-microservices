## Overview

The Loan Service manages the complete lifecycle of book loans within the Library Platform.

The service is responsible for handling loan requests, reservations, confirmations, cancellations and returns while coordinating with other services through 
asynchronous integration events.

The module adopts an Event Sourcing and CQRS architecture, using domain events as the source of truth and projections as optimized read models.

## Responsibilities

The service provides a centralized workflow for loan management and ensures that the loan process remains consistent across the distributed platform.

Core responsibilities include:

- loan request management;
- reservation management;
- loan confirmation;
- loan cancellation;
- book return processing;
- overdue loan monitoring;
- loan statistics generation;
- popular book reporting;
- user loan analytics.

## Architectural Role

The service acts as the orchestration point for the loan domain.

```text
API Gateway
   │
   ▼
Loan Service
   │
   ├── Loan Event Store
   ├── Loan Projections
   ├── RabbitMQ Integration Events
   └── Dashboard Read Models
   │
   ▼

```

The service coordinates domain processes through asynchronous communication and reacts to events published by other services.

## Domain Model

The core aggregate of the service is Loan Aggregate.

This aggregate manages the lifecycle of a loan and enforces all domain invariants.

Supported states include:

- PENDING
- RESERVED
- CONFIRMED
- CANCELED
- RETURNED
- FAILED

Allowed transitions are explicitly defined and validated within the aggregate to ensure consistency throughout the loan lifecycle.

## Architectural Patterns

The service implements several architectural patterns commonly used in enterprise systems:

- Domain-Driven Design (DDD)
- Event Sourcing
- CQRS
- Outbox Pattern
- Event Replay
- Event-Driven Communication

### Event Sourcing

The current state of the domain is derived from persisted domain events rather than direct state mutations.

The aggregate rebuilds its state by replaying historical events and validating event versions to ensure consistency.

Benefits include:

- complete auditability;
- historical traceability;
- replay support;
- deterministic recovery;
- event-driven integration.

### CQRS and Read Models

The service separates write operations from query operations.

Write operations are handled through aggregates and event persistence.

Read operations rely on dedicated projections optimized for querying.

Available projections include:

- Loan Projection
- Book Projection
- User Projection
- Popular Book Projection
- Daily Loan Statistic Projection
- User Loan Statistic Projection

This approach enables efficient queries while preserving a fully event-driven write model.

### Outbox Pattern

Event publication is implemented through the Outbox Pattern: this approach ensures transactional consistency between event persistence and event publication.

Domain events are persisted in both:

- the event store;
- the outbox table.

A scheduled publisher reads pending outbox entries and publishes integration events to RabbitMQ, ensuring reliable event delivery.

### Event Replay

The service supports rebuilding projections by replaying historical events stored in the event store.

Replay processing supports:

- projection recovery;
- projection evolution;
- consistency validation;
- rebuilding read models without modifying historical events.

Dedicated replay repositories rebuild temporary projections and promote them to production views only after successful completion.

## Event Processing

The service distinguishes between domain events and integration events used for inter-service communication.

### Domain Events

Domain events represent business changes within the Loan Service bounded context.

They are:

- generated by aggregates;
- persisted in the event store;
- used to rebuild aggregate state;
- transformed into integration events used for projection updates and inter-service communication;
- internal to the originating service.

### Integration Events

Integration events are generated from persisted domain events and published through RabbitMQ.

They provide stable contracts for communication with other services and allow the domain model to evolve independently from inter-service integrations.

The Outbox Pattern guarantees reliable publication of integration events and prevents data-loss scenarios during message delivery.

## Produced Events

The service produces the following domain events:

- LoanRequestedEvent
- LoanReservedEvent
- LoanConfirmRequestedEvent
- LoanConfirmedEvent
- LoanCanceledEvent
- LoanReturnedEvent
- LoanFailedEvent

Events are persisted in the event store and published asynchronously through the Outbox mechanism.

## Consumed Events

The service reacts to events published by other services.

### Book Service Events

Consumed events include:

- BOOK_REGISTERED
- BOOK_RESERVED
- BOOK_BORROWED
- BOOK_RESERVATION_REJECTED
- BOOK_BORROW_REJECTED

These events drive loan state transitions and projection updates.

### User Service Events

Consumed events include:

- USER_SUBSCRIBED
- USER_UNSUBSCRIBED
- USER_SUSPENDED
- USER_UNSUSPENDED
- LIBRARY_CARD_ASSIGNED

These events maintain user-related projections used by the loan domain.

## Dashboard and Analytics

The service provides administrative dashboards and reporting capabilities.

Examples include:

- overdue loans;
- loan trends;
- daily loan statistics;
- user loan statistics;
- most popular books.

These views are generated through dedicated projections continuously updated by domain events.

## Service Interactions

### Book Service

Consumes book-related events and publishes corresponding loan events.

### User Service

Consumes user-related events and maintains user projections used by business workflows.

### Notification Service

Publishes loan-related events that are consumed by the Notification Service to notify users about loan updates.

## Security

The service acts as an OAuth2 Resource Server and validates JWT tokens issued by Keycloak.

Authorization is role-based and supports:

- READER
- LIBRARIAN
- ADMIN

Roles are extracted directly from JWT claims and applied through Spring Security authorization rules.

Role-based access control affects both available operations and data visibility.

For example, readers can only access their own loans while administrative users can access the complete loan list.
